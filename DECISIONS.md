# DECISIONS.md — ApriReader for Android

Журнал значимых архитектурных и продуктовых решений. Читается человеком, который
не следил за каждым шагом разработки: **что решено, какие были альтернативы, почему так**.

Проект: нативное Android-приложение (Kotlin + Jetpack Compose + Material 3),
приватность-ориентированный ридер книг. Отдельный продукт, не порт Windows-версии
(Tauri + Rust + TypeScript).

---

## 1. Минимальная версия Android — API 26 (Android 8.0)

**Решение.** `minSdk = 26`, `targetSdk = 36`, `compileSdk = 36`.

**Альтернативы.** API 21 (максимальный охват, Compose это позволяет), API 24,
API 29 (полный scoped storage).

**Почему.** На API 26 доступны без костылей и без desugaring: `java.time`,
adaptive launcher icons, `PdfRenderer` в предсказуемом виде, и SAF с
`takePersistableUriPermission` в том поведении, на которое рассчитана архитектура
хранения. API 21–25 потребовали бы отдельной ветки логики доступа к файлам ради
~2–3% устройств. API 29+ отрезал бы аудиторию без выигрыша: SAF-подход одинаково
работает начиная с 26.

## 2. Структура — два Gradle-модуля, а не один и не десять

**Решение.** `:bookformat` (Android library, парсинг форматов, без UI-зависимостей)
и `:app` (данные, UI, виджет). Внутри `:app` — пакеты по фичам.

**Альтернативы.** Один модуль (быстрее стартовать); полноценная многомодульность
`core:*` / `feature:*` (модно, лучше изолирует).

**Почему.** Парсеры — единственная часть, которую действительно ценно
изолировать: они чистые, тестируются юнит-тестами без Android-инструментария и
не должны иметь возможности «случайно» потянуть Compose. Дробление UI на
feature-модули на проекте такого размера даёт больше накладных расходов на
сборку и конфигурацию, чем пользы.

## 3. DI — ручной AppContainer, не Hilt

**Решение.** Граф зависимостей собирается вручную в `AppContainer`, живущем в
`Application`. ViewModel'и создаются через `ViewModelProvider.Factory`.

**Альтернативы.** Hilt (стандарт де-факто), Koin.

**Почему.** Граф здесь неглубокий и почти статический. Hilt добавил бы второй
процессор аннотаций (KSP) и заметное время сборки ради удобства, которое на этом
объёме не окупается. Room остаётся единственным KSP-процессором в проекте.

## 4. Доступ к файлам — только SAF, без путей файловой системы

**Решение.** Импорт папок через `ACTION_OPEN_DOCUMENT_TREE`, отдельных книг через
`ACTION_OPEN_DOCUMENT`, немедленный `takePersistableUriPermission(READ)`.
Обход папки — курсорный, через `DocumentsContract.buildChildDocumentsUriUsingTree`.

**Альтернативы.** `READ_EXTERNAL_STORAGE` + прямые пути (на Android 11+ не
работает надёжно), `MANAGE_EXTERNAL_STORAGE` (требует обоснования в Google Play и
противоречит позиционированию по приватности).

**Почему.** Единственный способ, надёжно работающий на Android 11+, и
единственный, не требующий опасных разрешений. `DocumentFile.listFiles()` не
используется намеренно: он делает по запросу на файл и на больших библиотеках
работает на порядок медленнее курсорного обхода.

## 5. Идентичность книги — контентный ключ, а не URI

**Решение.** Стабильный `bookKey` = размер файла + хэш первых 64 КБ + нормализованное
имя файла. URI хранится как «текущий адрес» и может меняться.

**Альтернативы.** Ключ по document URI (просто, но ломается при переоформлении
доступа к папке или переносе файла).

**Почему.** Критерий приёмки требует, чтобы при отзыве и повторной выдаче доступа
прогресс чтения, закладки и статистика не терялись. URI этого не гарантирует.

## 6. Отзыв доступа к папке — штатный сценарий, не ошибка

**Решение.** Источники валидируются по `contentResolver.persistedUriPermissions`
перед сканом и перед открытием книги. Потерянный доступ не удаляет книги, а
помечает их `unavailable`; полка показывает баннер с повторным выбором папки.

**Почему.** Пользователь может отозвать доступ в системных настройках, переставить
SD-карту, удалить папку. Молчаливое исчезновение библиотеки — худший из возможных
вариантов поведения.

## 7. Парсинг форматов — собственные парсеры вместо готовых библиотек

**Решение.** EPUB, FB2, TXT, HTML, CBZ реализованы внутри `:bookformat` поверх
`java.util.zip` и `XmlPullParser`. Для CBR подключён **junrar** (Apache 2.0).
Для PDF — платформенный `android.graphics.pdf.PdfRenderer`.

**Альтернативы.** epublib (не поддерживается, тянет Java-API, отсутствующие на
Android), Readium Kotlin toolkit (мощный, но большой и навязывает свою модель
навигации и рендера), PdfBox-Android / Pdfium-wrapper (крупные нативные
зависимости).

**Почему.** EPUB и FB2 — это ZIP + XML; собственный парсер даёт полный контроль
над тем, как текст превращается во внутреннюю модель, что критично для
бионического шрифта и RSVP (им нужен доступ к потоку слов, а не к готовому HTML в
WebView). Плюс — ноль сторонних зависимостей, которые могли бы что-то отправлять в
сеть. junrar взят потому, что формат RAR закрытый и переписывать распаковщик
нецелесообразно; библиотека офлайновая, без сетевого кода.

## 8. Рендеринг текста — Compose Text, не WebView

**Решение.** Внутренняя модель `BookContent` = последовательность типизированных
блоков (параграф, заголовок, цитата, изображение, разрыв). Рендер — нативный
Compose.

**Альтернативы.** WebView с CSS-пагинацией (так делает большинство конкурентов —
проще получить точную вёрстку EPUB).

**Почему.** WebView делает невозможными два ключевых отличия продукта:
бионический шрифт (нужна пословная разметка с контролем веса) и RSVP (нужен
поток слов с таймингом). Плюс WebView — это отдельный сетевой стек внутри
приложения, что противоречит требованию «ни одного сетевого запроса без действия
пользователя». Цена решения — менее точная поддержка сложного EPUB-CSS; это
осознанный размен.

## 9. Сеть — OkHttp, включается только явным действием

**Решение.** Единственный сетевой клиент — OkHttp, создаётся лениво и вызывается
только из flow подтяжки метаданных, запущенного кнопкой пользователя. Никаких
аналитики, крашлитики, рекламы, IAP. В манифесте `INTERNET` присутствует, но ни
один компонент не обращается в сеть на старте.

**Почему.** Требование продукта. Coil сконфигурирован без сетевого загрузчика —
он используется только для локальных обложек.

## 10. Dynamic Cover Theming — Palette API + ручной оверрайд

**Решение.** Акцент извлекается из обложки через `androidx.palette`, затем
приводится к валидной MD3-схеме и проверяется на контраст (WCAG AA) с
автокоррекцией светлоты. Ручной акцент пользователя (для книги или глобальный)
имеет приоритет и никогда не перезаписывается авто-извлечённым.

**Почему.** Платформенный инструмент даёт приемлемую отправную точку; свой
алгоритм квантования цвета писать незачем. Коррекция светлоты нужна потому, что
«самый заметный» цвет обложки часто не проходит контраст как акцент.

## 11. Своя генерация схемы MD3 вместо внешней библиотеки

**Решение.** Тональные палитры строятся в CIELCh (`TonalPalette`), роли Material 3
расставляются вручную (`buildColorScheme`), поверх работает явная проверка
контраста по WCAG (`ensureContrast`).

**Альтернативы.** `material-kolor` или другая обёртка над HCT/CAM16;
`dynamicColorScheme` (работает только с обоями системы, а не с обложкой).

**Почему.** Публичного API для генерации схемы из произвольного семени в
`androidx.compose.material3` нет. LCh даёт результат, близкий к HCT, и не тянет
зависимость. Главное — контраст здесь не побочный эффект палитры, а явная
проверка с автокоррекцией светлоты; она покрыта тестами на восьми «трудных»
семенах в обеих темах и для всех стилей страницы.

## 12. Текстовый слой PDF — PDFBox-Android

**Решение.** Страницы PDF рисуются системным `PdfRenderer`; текст для RSVP,
бионики и поиска извлекается `com.tom-roush:pdfbox-android` лениво, по первому
требованию.

**Альтернативы.** Свой парсер PDF (нереалистично по объёму), отказ от текстовых
режимов в PDF (нарушил бы требование P0), Pdfium-обёртки (крупные нативные
зависимости).

**Почему.** Библиотека офлайновая, под Apache 2.0, без сетевого кода. Цена —
около 7 МБ в релизной сборке; текстовый слой не загружается, пока пользователь не
включит режим, которому он нужен.

## 13. Выделения — на уровне абзаца, а не произвольного диапазона

**Решение.** Долгое нажатие на абзац предлагает выделить его целиком или
поставить закладку.

**Альтернативы.** Посимвольное выделение с хэндлами поверх собственного рендера.

**Почему.** Собственный рендер текста (решение №8) означает, что хэндлы
выделения, их перетаскивание и попадание в глиф пришлось бы реализовывать
самостоятельно. Для читателя выигрыш от посимвольного выделения по сравнению с
абзацным невелик, а риск получить неточное и неудобное поведение — высокий.
Решение помечено как кандидат на пересмотр.

## 14. Прогресс — по «весу» глав, а не по номеру главы

**Решение.** Доля книги считается как сумма весов пройденных глав плюс позиция
внутри текущей; вес главы — её объём в символах.

**Почему.** Глава на две страницы и глава на сорок не могут стоить одинаково:
иначе прогресс скачет и не соответствует ощущению читателя.

## 15. Идентичность книги, ключ и виджет

**Решение.** Прогресс пишется через область корутин уровня приложения, а не
экрана, и после записи обновляется виджет домашнего экрана.

**Почему.** Экран чтения закрывается в тот же момент, когда прогресс нужно
сохранить; корутина, привязанная к ViewModel, была бы отменена на полпути.

## 16. Озвучивание — только системный TTS, без фонового сервиса

**Решение.** Чтение вслух через `android.speech.tts.TextToSpeech`. Очередь
формируется из абзацев текущей главы, озвучиваемый абзац подсвечивается и
удерживается в поле зрения, по окончании главы чтение продолжается со следующей.
Движок создаётся лениво — при первом нажатии «Вслух».

**Альтернативы.** Облачные TTS (лучше голоса), фоновое воспроизведение с
MediaSession и уведомлением.

**Почему.** Облачный синтез означал бы отправку текста книги на чужой сервер —
это прямо противоречит обещанию приватности. Фоновое воспроизведение требует
foreground-сервиса, отдельного уведомления и обработки аудиофокуса; это
самостоятельная задача, отложенная сознательно: сейчас голос живёт вместе с
открытым экраном чтения.

## 17. Перелистывание — прокрутка на экран, а не своя пагинация

**Решение.** Нажатие по краям экрана и кнопки громкости прокручивают текст ровно
на высоту окна минус перекрытие в две строки.

**Альтернативы.** Настоящая постраничная вёрстка с разбиением текста по
страницам и анимацией переворота.

**Почему.** Настоящая пагинация требует измерять текст при каждом изменении
типографики и заново раскладывать главу; при семи гарнитурах и свободных
настройках кегля, интерлиньяжа и полей это отдельный движок вёрстки. Прокрутка
на экран даёт читателю то же ощущение «страницы» и остаётся корректной при любых
настройках. Перекрытие в две строки оставлено намеренно: без него взгляд теряет
место стыка.

**Обработка кнопок громкости** сделана через `dispatchKeyEvent` активити, а не
через фокус в Compose: фокусируемый контейнер поверх текста мешал бы TalkBack.

## 18. Lint как часть сборки

**Решение.** `abortOnError = true`, проверка зависимостей включена; отключено
только предупреждение `TrustAllX509TrustManager`, приходящее из bouncycastle
внутри PDFBox.

**Почему.** На первом же запуске lint нашёл вызов `SortedSet.reversed()`,
который компилируется, но уходит в `java.util.SequencedCollection#reversed` из
API 35 и упал бы в рантайме на всех устройствах ниже Android 15. Такие ошибки
компилятор Kotlin не ловит, а тесты бы поймали только на устройстве.

## 19. Из виджета исключён WorkManager

**Решение.** `androidx.glance:glance-appwidget` и `glance-material3` подключены с
`exclude(group = "androidx.work")`.

**Что произошло.** Проверка собранного APK через `aapt dump badging` показала в
манифесте четыре разрешения, которых в исходниках нет: `WAKE_LOCK`,
`ACCESS_NETWORK_STATE`, `RECEIVE_BOOT_COMPLETED` и `FOREGROUND_SERVICE`. Отчёт
слияния манифестов указал на `androidx.work:work-runtime`, приходящий транзитивно
вместе с Glance.

**Почему исключено.** В классах `glance-appwidget:1.1.1` нет ни одной ссылки на
`androidx.work` — зависимость осталась от прежних версий. При этом её присутствие
меняет то, что видит пользователь в карточке Google Play: читалка, которая просит
разрешение на автозапуск при загрузке устройства и на foreground-сервис, выглядит
ровно так, как приложения, от которых этот проект отстраивается. После исключения
в APK остаются `INTERNET` и подписное разрешение
`com.aprireader.app.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` — оно объявляется
самим приложением, имеет уровень защиты «signature» и наружу ничего не открывает.

**Урок в процесс.** Список разрешений проверяется по собранному APK, а не по
исходному манифесту: транзитивные зависимости дописывают в него своё.

## 20. Подпись: ключ разработчика отдельно от ключа публикации

**Решение.** В репозитории лежит только шаблон `keystore.properties`; сам ключ и
файл свойств не коммитятся (`.gitignore`). Для локальной установки собранного
релиза используется самоподписанный ключ разработчика.

**Почему.** Ключ загрузки в Google Play должен создать и хранить владелец
приложения: его потеря означает невозможность обновлять приложение. Ключ,
созданный в ходе разработки, для этого не годится и помечен как отладочный.

## 21. Что нашло ревью перед релизом

Дефекты, найденные вычиткой кода, а не тестами, — вместе с тем, почему они
возникли. Список полезен как список типовых ловушек этого проекта.

1. **Переход из поиска не работал.** `openHit` выставлял целевой абзац сразу, а
   `openChapter` дописывал состояние позже, уже после загрузки главы, и затирал
   цель значением `null`. Целевой абзац теперь вычисляется внутри `openChapter`.
   Общее правило: состояние, зависящее от асинхронной загрузки, нельзя выставлять
   до неё.
2. **Выход из RSVP в PDF ронял читателя в текстовый слой.** Режим восстанавливался
   по наличию текстовой сессии, а она появлялась как побочный эффект самого RSVP.
   Теперь запоминается режим, из которого пользователь ушёл.
3. **Полка сортировала названия от Я к А.** Флаг «по возрастанию» трактовался
   по-разному для разных сортировок. Теперь он означает буквально возрастание, а
   при выборе сортировки направление сбрасывается на естественное для неё. На
   поведение написан регрессионный тест.
4. **Гонка при поиске по PDF.** Поиск и чтение грузят главы параллельно, а PDFBox
   не потокобезопасен: два одновременных прохода по `PDDocument` роняют процесс.
   Загрузка главы сериализована мьютексом, кэш остался под своим замком.
5. **Два движка TTS.** Инициализация `TextToSpeech` асинхронная, и два быстрых
   нажатия «Вслух» создавали второй экземпляр, а первый оставался в памяти.
   Добавлен флаг инициализации.
6. **Чтение настроек блокировало главный поток на старте.** `runBlocking` по
   DataStore давал корректную тему с первого кадра ценой дисковой операции в UI-
   потоке. Заменено удержанием сплэш-экрана до первого значения настроек.
7. **Импорт PDF был неоправданно тяжёлым.** Ради одного заголовка каждый PDF
   копировался в кэш и полностью разбирался PDFBox. Теперь при импорте работает
   системный `PdfRenderer`: он даёт число страниц без копии файла, а первая
   страница становится обложкой. Текстовый слой поднимается только тогда, когда
   пользователь включает RSVP, бионику или поиск.

## 22. Ключ подписи и артефакт для Play

**Решение.** В Play загружается `app-release.aab`; APK остаётся только для
ручной установки и тестирования. Ключ загрузки создаёт владелец приложения,
включается Play App Signing.

**Почему.** Google Play с 2021 года принимает только Android App Bundle. Play App
Signing снимает риск потери ключа подписи приложения: владелец отвечает лишь за
upload key, который можно перевыпустить.

## 23. Визуальное направление: Material 3 на жидком стекле

**Решение.** Material 3 остаётся системой (цветовые роли, типографическая шкала,
компоненты, motion), а поверхностный слой переведён на «жидкое стекло»:
полупрозрачные панели, окрашенные акцентом текущей книги, со сглаженными углами
и бликом по верхней кромке.

**Три составляющие.**

1. **Сглаженные углы.** `SquircleShape` — наследник `CornerBasedShape`, где угол
   не дуга окружности, а кубическая кривая с касательными вдоль граней. Кривизна
   меняется непрерывно, и угол перестаёт читаться как фаска. Наследование от
   `CornerBasedShape` выбрано не случайно: тема Material 3 принимает только такие
   формы, поэтому кнопки, чипы, диалоги и меню получают новую геометрию без
   правки каждого места вызова. Радиусы подняты (10–36 dp): при 4–8 dp
   сглаживание не различимо и вся затея бессмысленна.

2. **Стекло, окрашенное книгой.** Панели не нейтрально-серые: в подложку
   подмешивается акцент текущей обложки, а под карточкой «продолжить чтение»
   цветёт размытая обложка. Это связывает новый визуальный слой с тем, что и так
   было главной идеей продукта, — интерфейс принимает цвет того, что вы читаете.

3. **Третья типографическая роль.** Заголовки интерфейса переведены на
   Bricolage Grotesque (переменные вес и ширина). Inter остался служебным слоем,
   Literata — только чтением. Разделение слоёв чтения и интерфейса сохранено.

**Честно про размытие.** Настоящего backdrop-блюра в Compose нет: `Modifier.blur`
размывает собственное содержимое элемента, а не то, что под ним. Тянуть
стороннюю библиотеку ради этого не стали. Ощущение стекла строится на трёх
вещах, работающих на всех поддерживаемых версиях: плотность подложки,
вертикальный градиент (сверху светлее, как отражение неба) и светлая кромка.
Настоящее размытие применяется там, где оно возможно, — к ореолу обложки, и
только на Android 12+; ниже остаётся радиальный градиент акцента.

**Прозрачность не отменяет читаемости.** Плотности стекла подобраны не на глаз:
`GlassContrastTest` берёт шесть цветов-семян, обе темы, три уровня плотности и
семь худших подложек (белая и чёрная страница, бумага, сепия, кислотные
обложки) и проверяет, что текст на композите проходит WCAG AA. Сделать стекло
прозрачнее без пересчёта этого теста нельзя.

**Проверка формы без устройства.** Squircle нельзя оценить на глаз в коде,
поэтому та же математика была отрисована в Java2D и сравнена с обычным
скруглением: при `smoothing = 0.6` угол читается как непрерывный, при `1.0`
форма превращается в подушку. Отсюда и значение по умолчанию.

## Отложено осознанно (P2, вне скоупа этой версии)

- **Аудиокниги.** Отдельная модель воспроизведения, MediaSession, форматы
  M4B/MP3-глав — по объёму сравнимо со всем ридером. Не смешивать с текстом.
- **Фоновое озвучивание.** Голос сейчас работает только при открытом экране
  чтения. Продолжение при выключенном экране требует foreground-сервиса,
  уведомления с управлением и корректной работы с аудиофокусом — см. решение №16.
- **Перевод текста по выделению.** Любой качественный перевод требует сетевого
  сервиса, то есть отправки фрагментов книги наружу. Это не запрещено (действие
  явное), но требует отдельного продуманного consent-флоу и выбора провайдера —
  решение осознанно отложено.
- **Облачная синхронизация библиотеки и прогресса.** Жёсткое ограничение версии.
